# Acceptance, QA, And Handoff

This document defines how MSD-001 should prove itself.

The milestone should be judged by working delivery evidence, not by how many
new files or agents exist.

## Golden Scenario

Use a small multi-service task tracker as the golden scenario.

### Requirements

```text
Create a small internal task tracker.

Feature 1:
- The API can create and list tasks.
- The web UI can submit a task title and show the task list.

Feature 2:
- The API can mark a task as done.
- The web UI can toggle a task between open and done.

Use a simple in-memory store for now.
Run locally with Docker Compose.
Deploy to Azure dev resources after QA passes.
```

### Expected Generated Shape

```text
generated-project/
  api/
  web/
  docker-compose.yml
  Dockerfile.api
  Dockerfile.web
  pyproject.toml
  uv.lock
  README.md
```

### Expected Delivery Shape

```text
Planning artifacts
Fullstack implementation artifacts
QA strategy and report
Deployment plan/request/summary
Deployment-owned smoke evidence
Handoff report
```

## Milestone Acceptance Criteria

| Area | Acceptance Criteria |
| --- | --- |
| Planning | Produces a feature queue with two feature items and testable acceptance criteria. |
| Fullstack | Generates API + web project using stable layout and Docker names. |
| QA | Creates a strategy mapping features to checks and evidence. |
| QA | Validates API endpoints, web UI, Docker runtime, and browser integration. |
| Repair | Failed QA can route to Fullstack repair with max 3 attempts. |
| Deployment | Detects API/web topology and deploys or blocks with a useful reason. |
| Deployment | Reuses stable dev resources and persists public URL(s). |
| Deployment Smoke | Deployment Agent validates that the deployed dev runtime is reachable and basically healthy. |
| Post-deploy QA | Full QA-owned post-deployment validation is deferred to the next AgentExecutor/inter-agent milestone. |
| Post-deploy Repair | Runtime failure routing between Fullstack, QA, and Deployment is deferred with post-deploy QA. |
| Handoff | Writes a stakeholder-ready report with feature, QA, deployment, URL, evidence, and limitations. |
| Console | Shows active stage, agent, feature status, QA status, repair attempts, and deployment URLs. |
| Tests | Unit/integration tests cover new contracts and routing behavior. |

## Autonomous QA Strategy Requirements

The QA Agent should write strategy before running checks. The strategy is not a
fixed platform checklist for known demo features. It is produced by the QA
Codex agent from the active feature, completed-feature context, generated
implementation, and planning artifacts.

Required strategy sections:

- requirements summary,
- detected topology,
- feature acceptance map,
- planned checks,
- required tools,
- generated test scripts,
- evidence paths,
- risk/gap list.

The structured strategy can include:

```text
command checks
python_script checks generated by the QA Agent
temporary script packages such as Playwright via `uv run --with`
manual_gap checks when automation is missing
```

Required `manual_gap` checks fail the feature until the QA Agent can produce or
select executable evidence.

Example check mapping:

| Feature | Criterion | Check | Evidence |
| --- | --- | --- | --- |
| F1 | API creates tasks | API endpoint test | `qa/api/create-task.json` |
| F1 | Web submits tasks | Browser test | `qa/screenshots/web-create-task.png` |
| F2 | API marks done | API endpoint test | `qa/api/mark-done.json` |
| F2 | Web toggles status | Browser test | `qa/screenshots/web-toggle-task.png` |

## Implementation Repair Acceptance

The implementation repair loop must be evidence-driven.

Required behavior:

1. QA fails a specific criterion.
2. QA writes `10-fix-request.md` and `10-fix-request.json`.
3. The delivery graph increments `repair_attempts`.
4. Fullstack receives fix request and evidence references.
5. Fullstack makes the smallest relevant repair.
6. QA reruns.
7. If QA passes, deployment continues.
8. If QA fails after 3 attempts, run becomes blocked.

The platform should never silently skip failed QA to deploy.

## Post-Deployment QA And Repair Deferral

Post-deployment QA should eventually be a Quality Agent validation mode that
runs against the public deployed runtime. That remains the intended ownership
model, but it is not required for MSD-001 closure.

For MSD-001, Deployment Agent-owned smoke validation is the accepted proof that
the deployed dev runtime is reachable and basically healthy. The handoff report
must describe this honestly as deployment smoke evidence, not as a separate QA
Agent post-deploy pass.

Deferred target behavior:

1. Deployment writes public URL(s) and resource details.
2. Quality Agent runs post-deployment QA against the public web URL.
3. Quality Agent records evidence separately from pre-deployment QA.
4. If post-deploy QA passes, Handoff can run.
5. If post-deploy QA fails because application behavior is wrong, Quality Agent
   writes a Fullstack fix request.
6. Fullstack repairs the application.
7. Implementation QA reruns.
8. Deployment updates the affected resource(s).
9. Post-deployment QA reruns.
10. If post-deploy QA fails because infrastructure/configuration is wrong,
    Quality Agent routes the issue to Deployment Agent.
11. Deployment repairs or retries the deployment.
12. Post-deployment QA reruns.
13. If attempts are exhausted, the run blocks and Handoff may only write a
    blocked handoff summary.

This creates two loops:

```text
Fullstack <-> QA
Deployment <-> QA
```

with QA acting as the evidence-producing judge, not the repair owner.

This deferred loop should be handled in the next AgentExecutor/inter-agent
communication milestone, where Deployment can hand public runtime targets to QA,
QA can classify deployed-runtime failures, and the company graph can route the
result to Fullstack or Deployment.

## Deployment Acceptance

Deployment should be autonomous without pretending it supports everything.
Deployment Codex owns topology discovery from generated project evidence. The
platform validates the output contract; it does not hardcode a list of accepted
service shapes.

Required behavior:

- infer topology from Docker Compose, Dockerfiles, source layout, README,
  environment examples, and QA evidence;
- build/push API and web images or use a documented supported strategy;
- reuse stable Azure dev resources;
- configure web service with API base URL;
- report deployed public URL(s) and run deployment-owned smoke validation;
- write public URL(s) to deployment summary and graph state;
- for repeat releases, inspect existing dev resources first and update/reuse
  them instead of creating a parallel stack;
- summarize each resource as reused, updated, created, skipped, or blocked;
- retry deployment-owned failures without sending infrastructure work to
  Fullstack;
- block with an actionable message for unsupported, unsafe, ambiguous, or
  credential-blocked deployment.

## Stable Naming Policy

The platform should avoid creating new resources or Docker images for every run
during local/dev iteration.

Recommended Docker names for the current sample when they fit inferred topology:

```text
compose project: agentic-dev
api image: agentic-api:latest
web image: agentic-web:latest
api container: agentic-api-dev
web container: agentic-web-dev
```

Recommended Azure names:

```text
resource group: rg-agentic-dev
container apps env: agentic-dev-env
registry: agenticdevacr
api container app: app-agentic-api-dev
web container app: app-agentic-web-dev
```

If generated project names differ, Deployment Codex should normalize dev target
names unless production mode explicitly asks for unique names. It may adapt this
policy when the actual topology requires it, but it must keep names short and
explain the decision.

## Handoff Report Standard

The handoff report should be good enough for a non-engineering stakeholder.

Required sections:

```text
# Handoff Summary

Status
Project
Delivered Features
Public URL(s)
How To Use
QA Summary
Deployment Summary
Evidence
Known Limitations
Recommended Next Steps
```

### Delivered Features Section

Example:

```text
## Delivered Features

| Feature | Status | Notes |
| --- | --- | --- |
| F1 - Create and list tasks | delivered | Passed API, web, Docker, and browser checks. |
| F2 - Mark tasks done | delivered | Passed API and browser toggle checks. |
```

### Evidence Section

Evidence should link to artifacts:

```text
- QA results: `qa/results-F1.json`, `qa/results-F2.json`
- QA Codex logs: `qa/codex/F1/*`, `qa/codex/F2/*`
- QA report: `08-qa-report-F1.md`, `08-qa-report-F2.md`
- QA-created helper scripts/evidence, if any: `qa/...`
- QA fix request, when needed: `10-fix-request-Fx.md/json`
- Deployment summary: `13-deployment-summary.md`
- Browser screenshot: `qa/screenshots/api-web-after.png`
- Browser transcript: `qa/browser/api-web-transcript.json`
```

Do not paste long logs into the handoff.

## Test Plan For The Platform Itself

The platform implementation should add tests in the existing grouped structure:

```text
tests/unit/agents/planning/
tests/unit/agents/fullstack/
tests/unit/agents/quality/
tests/unit/agents/deployment/
tests/unit/agents/handoff/
tests/unit/orchestration/
tests/unit/console/
tests/unit/integrations/
tests/integration/
```

Minimum tests:

- planning feature queue model/schema,
- implementation brief includes feature IDs,
- Fullstack prompt includes stable multi-service naming rules,
- QA strategy maps acceptance criteria to checks,
- QA fix request includes feature/check/evidence references,
- repair loop routes fail -> repair -> QA,
- repair loop blocks after 3 attempts,
- deployment-owned smoke evidence is represented without claiming a separate
  QA Agent post-deploy pass,
- deployment topology detection,
- deployment summary includes multiple public URLs when applicable,
- handoff report includes required sections and feature table.

## Non-Goals For Acceptance

MSD-001 does not need to prove:

- arbitrary user authentication,
- persistent database migrations,
- production-grade API security,
- arbitrary microservice topologies,
- cloud portability,
- full PDF export,
- true parallel agent work,
- support for all 20 future agents.

It does need to prove that the platform can manage a richer delivery workflow
with clean agent ownership.
